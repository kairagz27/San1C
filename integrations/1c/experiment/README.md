# Файловый стенд нативной выгрузки

## Двухнедельный пилот

Для этого сценария предусмотрен отдельный экземпляр `https://localhost:8448` с собственной PostgreSQL и двумя паролями. Нативная ИБ, скомпилированные файлы, журналы и CSV создаются в новом каталоге `%LOCALAPPDATA%\San1C\lab\pilot-runs`. Проект Compose называется `san1c-lab-pilot`. Адреса 8446 и 8447 сохраняют исходные отдельные эксперименты. Если несколько раз повторить сценарий на 8448, последний успешный снимок заменяет предыдущий за тот же день. Сохранённые сверки остаются доступны с отдельными идентификаторами.

```powershell
$designer = Join-Path $env:LOCALAPPDATA 'Programs\San1C-Lab\file-platform\1cv8t\8.5.1.1343\bin\1cv8t.exe'
py -3 integrations/1c/lab/transport/lab.py up pilot
py -3 integrations/1c/experiment/pilot.py --platform "$designer"
```

При первом открытии Конфигуратор уже собрал **два разных файла в каталоге текущего прогона**. Проверьте путь каждого и разово подтвердите открытие в 1С. `San1CВыгрузка.epf` — сценарий стенда с документами, контрольным запросом и квитанциями. **`San1CАдаптер.epf`** — обычная форма проверки подключения и отправки с двумя текстовыми макетами, без лабораторных команд создания или изменения документов. Этот адаптер реально вызывают ручная двухнедельная выгрузка и обработчик расписания. В исполняемой учебной конфигурации задан путь только к этим собственным сборкам. Она открывает их с правом доступа к локальным файлам и HTTPS. Права на каталог прогона ограничены. На копии УТ сначала нужен адаптер с соответствующим профилем. Учебный бинарный файл содержит профиль «УчебнойТорговли».

Сценарий последовательно выполняет исходную однодневную регрессию, загружает 09–22.11.2026, повторяет 14 дней, меняет и перепроводит сумму продажи за 09.11, затем отменяет проведение и повторяет этот день. Вторая точка продаёт не каждый день. За 11.11 обе точки имеют подтверждённый ноль. Контроли из 1С используют отдельный агрегирующий запрос по двум документам, дате и точке. Сценарий проверяет все три суммы и число документов по каждому дню и точке, сравнивает суммарные отчёты и читает сохранённый результат сверки обратно из API. Имена фаз в квитанциях — `first`, `repeat`, `seed14`, `repeat14`, `correct`, `unpost`.

После ручных этапов 1С регистрирует настоящее задание «УчебнаяВыгрузкаПродаж» и оставляет файловый клиент открытым. Пробное расписание задаёт повторы через 30 секунд. Платформа опрашивает задания файловой базы примерно раз в минуту и может инициализировать планировщик до 120 секунд. При первой попытке лаборатория передаёт заведомо недействительный токен и сохраняет отказ, при следующих двух использует действующий. Каждая успешная попытка повторяет последние **три закрытых дня по времени сеанса**. После получения трёх результатов контроллер выключает задание. Разовое окно подтверждения EPF требуется при установке собственной сборки, сам фоновый этап проходит без действий пользователя. Для УТ нужен выбор реального способа регистрации и отдельный прогон под учётной записью клиента. [Регламентные задания в 1С](https://v8.1c.ru/platforma/reglamentnoe-zadanie/) · [Механизм заданий в файловом режиме, раздел 19.4](https://1c-dn.com/download-trial/files/guides/developer_guide.pdf)

В каталоге прогона `native-*.json` и `scheduled-*.json` содержат результаты от 1С, `api-*.json` — действительные значения дневной детализации San1C, `control-*.csv` — выгрузки независимого контроля 1С, `reconciliation-*.json` — сохранённые результаты сравнения. `control-final.csv` включает две точки и 14 дней после исправления и снятия проведения. Проверка с `--work-dir` требует нового каталога, чтобы защитить ранее созданную ИБ.

## Исходная однодневная регрессия

23 ноября 2026 года на учебной платформе **1С:Предприятие 8.5.1.1343** прошёл полный прогон. Конфигуратор создал файловую ИБ `УчебнаяТорговля` версии `1.0.0.1` и собрал внешнюю обработку. В клиенте 1С она прочитала проведённые документы встроенным запросом и дважды отправила результат в San1C по HTTPS. Для проверки «1С:Управление торговлей для Казахстана» ещё предстоят сопоставление метаданных конкретного релиза и сверка на базе клиента.

## Состав

| Дата и фильтры | Продажи с НДС | Возвраты с НДС | Выручка | Документы продажи |
| --- | ---: | ---: | ---: | ---: |
| 16.11.2026, все точки | 10 000 ₸ | 2 000 ₸ | 8 000 ₸ | 1 |
| 16.11.2026, «Учебная точка» | 10 000 ₸ | 2 000 ₸ | 8 000 ₸ | 1 |

Эти значения совпали в контрольном запросе 1С и рабочих отчётах API после каждого запуска. Квитанции 1С содержат HTTP 200, `accepted` и две строки с метками `2026-11-23T05:28:03Z` и `2026-11-23T05:28:17Z`. После повторной передачи API подтвердил тот же день с двумя строками. На компьютере прогона доказательства лежат в `%LOCALAPPDATA%\San1C\lab\native-runs\20261123-102735-eb04f218`. Файлы `native-first.json` и `native-repeat.json` записала 1С, а `api-first.json` и `api-repeat.json` содержат наблюдения HTTP API после соответствующих отправок.

В конфигурации четыре справочника и два типа проводимых документов. Первый запуск в одной транзакции создаёт организацию, точку, категорию, товар и два документа по одной позиции. В продаже пять единиц товара по 2 000 ₸, в возврате одна. Обработка затем самостоятельно запускает контрольный запрос с суммированием и подсчётом документов. Второй запуск читает те же проведённые документы из той же ИБ.

Исходники XML для Конфигуратора лежат в `configuration/` и `processor/`. Перед сборкой `run.py` наполняет макеты «Профиль» и «ЗапросДня» из `../profiles/educational/`, копирует основной BSL-модуль и форму обработки, добавляет к ним `ExperimentObject.bsl` и `ExperimentForm.bsl`. Только эта отдельная сборка распознаёт локальное задание, создаёт контрольные документы и сохраняет результаты. Кнопка обычной обработки по умолчанию использует системные корневые сертификаты. В форме доступно поле для приватного CA. Учебный запуск передаёт ей файл CA из частного каталога стенда.

## Запуск в Windows

1. Установите учебную платформу с Конфигуратором или воспользуйтесь подготовленной локальной копией на компьютере прогона. Учебная версия поддерживает файловые ИБ и один сеанс. Скрипт последовательно запускает Конфигуратор и клиент «1С:Предприятие». Формат XML здесь **2.17**, совместимость конфигурации **8.3.24**, фактическая версия проверенной платформы **8.5.1.1343**. [Учебная версия и ограничения](https://v8.1c.ru/podderzhka-i-obuchenie/uchebnye-versii/distributiv-1s-predpriyatie-8-3-versiya-dlya-obucheniya-programmirovaniyu/), [формат выгрузки конфигураций](https://1c-dn.com/library/tutorials/1c_enterprise_developer_guide_8_3_27/).
2. Поднимите отдельный нативный экземпляр San1C с HTTPS на `https://localhost:8446`. Установите серверный профиль `integrations/1c/profiles/educational/experiment.json`, перенеся его вместе с `query.1cq`. По умолчанию файлы транспорта лежат в `%LOCALAPPDATA%\San1C\lab\transport\native`. Требуются `ca.pem` с доверенным для этого стенда УЦ и частный `credentials.json` с полем `upload_token`. Разрешите доступ только пользователю стенда. Оба файла остаются за пределами исходников. Пароль веб-интерфейса обработка не использует.
3. Из корня репозитория укажите фактический путь к **толстому клиенту с Конфигуратором**. В учебной Windows-установке ищите `bin\1cv8t.exe` в каталоге версии, в обычной установке — `bin\1cv8.exe`. В PowerShell можно перечислить оба варианта и выбрать нужный установленный релиз.

   ```powershell
   Get-ChildItem "$env:ProgramFiles\1cv8*\*\bin\1cv8*.exe", "${env:ProgramFiles(x86)}\1cv8*\*\bin\1cv8*.exe" -ErrorAction SilentlyContinue |
       Where-Object Name -in '1cv8t.exe','1cv8.exe' | Select-Object -ExpandProperty FullName
   $platformExe = Read-Host 'Полный путь к выбранному исполняемому файлу'
   py -3 integrations/1c/experiment/run.py --platform $platformExe
   ```

   На компьютере этого прогона вместо системной установки можно использовать подготовленный каталог пользователя. Сверьте SHA-256 файла с проверенным экземпляром и запустите тот же сценарий.

   ```powershell
   $platformExe = Join-Path $env:LOCALAPPDATA 'Programs\San1C-Lab\file-platform\1cv8t\8.5.1.1343\bin\1cv8t.exe'
   if ((Get-FileHash -Algorithm SHA256 -LiteralPath $platformExe).Hash -ne '0A85010EA475DF6379667AEEBDE6ED906C5DE23FE491A5F55FEF5A78FBB270CE') { throw 'SHA-256 клиента отличается от экземпляра прогона' }
   py -3 integrations/1c/experiment/run.py --platform $platformExe
   ```

4. При первом открытии собранной EPF пользователь должен утвердительно ответить в штатном диалоге защиты. Проверьте, что в предупреждении указан файл `San1CВыгрузка.epf` из напечатанного каталога прогона, и подтвердите его открытие. Запускайте скрипт в интерактивном сеансе Windows. При повторном приглашении подтвердите открытие того же файла. В каталоге сохраняются `db/1Cv8.1CD`, EPF, журналы команд, файлы заданий и результаты 1С. В обеих квитанциях ожидаются `ok=true` и показатели из таблицы.
5. После каждой квитанции runner читает через HTTPS покрытие и четыре показателя рабочего отчёта за 16.11.2026 по всем точкам и с фильтром «Учебная точка». Файл `api-first.json` содержит наблюдение до запуска повторной отправки, `api-repeat.json` — наблюдение после неё. Проверьте даты, фильтры, суммы, число документов, количество строк и последнее событие журнала. При расхождении runner сохраняет полученные значения и останавливается. Ключ `--transport-dir` задаёт общий каталог `ca.pem` и `credentials.json` для обработки и проверки API.
5. Откройте рабочий режим нативного стенда. В отчёте выберите 16.11.2026, сначала все точки, затем «Учебная точка». Сравните четыре показателя с таблицей. В источнике ожидаются две успешные выгрузки за одну дату и подтверждённое покрытие дня. Уникальные строки должны остаться в количестве двух. Более поздняя метка при повторе может дать ответ `accepted`. Оба допустимых ответа `accepted` и `unchanged` должны содержать ту же дату и количество строк.

### Команды платформы и диагностика

Скрипт передаёт в Конфигуратор `CREATEINFOBASE`, `DESIGNER /LoadConfigFromFiles`, `/UpdateDBCfg` и `/LoadExternalDataProcessorOrReportFromFiles`. После штатной сборки запускает два отдельных `ENTERPRISE /Execute San1CВыгрузка.epf /C SAN1C-LAB:<путь задания>`. Для каждого процесса устанавливается тайм-аут. Изменить его можно ключом `--timeout 600`. Новый каталог можно назначить через `--work-dir`, путь транспорта — через `--transport-dir`. [Пакетный режим Конфигуратора](https://1c-dn.com/1c_enterprise/designer_batch_mode/).

При ошибке Designer откройте пронумерованный журнал указанного этапа. Если клиент не оставил квитанцию, проверьте, что форму обработки удалось открыть и сеанс имеет доступ к файлам задания, CA и токена. Если квитанция содержит `ok=false`, поле `stage` различает запись данных, контрольный запрос и исходящий HTTPS. В `message` возможен безопасный HTTP-код. Содержимое документов и ключи в свидетельства не включаются. При разборе состояния откройте созданную ИБ и готовую обработку вручную.

Для подготовки комплекта исходников до установки платформы:

```powershell
py -3 integrations/1c/experiment/run.py --prepare-only
```

Команда готовит XML и BSL в новом каталоге. При разработке статически проверена структура XML конфигурации, справочников, документов, обработки и формы. BSL Parser 0.41.1 разобрал оба итоговых модуля, шаблон выгрузки и отдельный контрольный запрос. Штатная сборка и передача из клиента 1С проверены отдельным запуском с `--platform`. [BSL Parser](https://github.com/1c-syntax/bsl-parser).

XML составлен из собственных определений объектов и формы. Для создания и статической структурной проверки использованы генераторы проекта `cc-1c-skills`, ревизия `4fc37e1f992057847228a69837337bd3c141c059`. Лицензия MIT включена в `METADATA-LICENSE.txt`. Для сборки приложенных исходников достаточно самой платформы и Python. [Исходники генераторов](https://github.com/Nikolay-Shirokov/cc-1c-skills/tree/4fc37e1f992057847228a69837337bd3c141c059).
